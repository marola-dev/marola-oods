## Rules for this bucket (on top of SKILL.md's Safety)

1. Default to read-only: `list-objects-v2`, `list-object-versions`, `head-object`, `get-object`
   to a temp file. Nothing else without a person.
2. Never run `b2 account get`, `b2 account clear` or any `b2 key *`; never read
   `~/.b2_account_info` or any `*b2_account_info*` file (the B2 CLI's credential database).
3. A delete, a lifecycle change, a bucket-type change: the dry run or the exact rule first, shown
   to the person, then their typed "yes". Anything else aborts.
4. Never make the bucket public. Never write a key, key id or account id to a file.
5. Bounded listings: page through, print at most 50 sample rows, summarise by prefix.

## Versions and hide markers

B2 buckets are always versioned. Through the S3 API, `ListObjectVersions` and
`GetObject?versionId=` work, and a B2 hide marker shows up as a `DeleteMarker`
([S3-compatible calls](https://www.backblaze.com/docs/cloud-storage-call-the-s3-compatible-api)).
Every upload of the catalog leaves the previous one as a version; a hidden or overwritten file is
still stored, and billed, until a lifecycle rule deletes it.

Wait at least 1 s between two writes of the same key (the catalog), or the two versions can
collide. AWS CLI v2's default CRC32 checksums are accepted; `AWS_REQUEST_CHECKSUM_CALCULATION=when_required`
is harmless to keep.

Restoring a version: [recovery.md](recovery.md) §4.

## Lifecycle: keep prior versions for 30 days

What the settings mean ([lifecycle rules](https://www.backblaze.com/docs/cloud-storage-lifecycle-rules)):
"Keep only the last version" is `daysFromHidingToDeleting: 1`; "Keep prior versions for this number
of days: N" is `daysFromHidingToDeleting: N`; rules run once a day.

**Recommend "Keep prior versions for this number of days: 30"** (`daysFromHidingToDeleting: 30`),
not "Keep only the last version": with 1 day, a bad catalog upload or an over-eager cleanup can be
undone for a day at most; with 30, the catalog and every Parquet file cleanup deleted stay
restorable for the same 30 days the lake keeps its snapshots. The cost is the old versions'
bytes, small at this bucket's size (below). The B2-native rule:

```json
[{"fileNamePrefix": "", "daysFromUploadingToHiding": null, "daysFromHidingToDeleting": 30}]
```

Through the S3 API the equivalent is `NoncurrentVersionExpiration: {NoncurrentDays: 30}`, and
`AbortIncompleteMultipartUpload` is accepted; `NewerNoncurrentVersions` and transitions return
400, and a put replaces every rule on the bucket. Setting it is a person's step (web UI: Buckets
→ Lifecycle Settings); an agent proposes the exact rule and reads it back afterwards.

## The two keys

| Key | Who | Capabilities | Where |
|---|---|---|---|
| read-write (the ETL key) | `oods-lake` jobs, a person's `--b2` run, maintenance | `listBuckets`, `listFiles`, `readFiles`, `writeFiles`, `deleteFiles`, this bucket only | GitHub: `BACKBLAZE_ETL_KEY_ID`, `BACKBLAZE_ETL_KEY_NAME` (variables), `BACKBLAZE_ETL_APP_KEY` (secret); the workflow maps them to `OODS_S3_KEY_ID`/`OODS_S3_SECRET` |
| read-only | marola-site, marola-ml, inspection | `listBuckets`, `listFiles`, `readFiles`, this bucket only | not created yet (MIP-0075 §5.6, a person's step) |

Least privilege: bucket-scoped, no key-management capability (`writeKeys`, `deleteKeys`), one
key per workload. A bucket-scoped key answers "bucket not found", not "unauthorized", for any other
bucket. A key that appears in the chat or a log: tell the person to rotate it, do not repeat it.

## How big is it: live vs billable

Billable storage is every version, not just the live files. The audit, read-only:

```bash
AWS_ACCESS_KEY_ID="$OODS_S3_KEY_ID" AWS_SECRET_ACCESS_KEY="$OODS_S3_SECRET" AWS_DEFAULT_REGION=us-east-005 \
  aws --endpoint-url https://s3.us-east-005.backblazeb2.com s3api list-object-versions \
  --bucket br-open-ocean-data-storage --output json \
  --query '{live: sum(Versions[?IsLatest].Size), noncurrent: sum(Versions[?!IsLatest].Size), versions: length(Versions), hide_markers: length(DeleteMarkers || `[]`)}'
aws ... s3api list-multipart-uploads --bucket br-open-ocean-data-storage   # unfinished uploads are billed too
```

The live Parquet alone, from DuckDB (metadata only, never `content`):

```sql
-- needs: b2
SELECT count(*) AS files, sum(size) AS bytes FROM read_blob('s3://br-open-ocean-data-storage/lake/**');
```

The same on the local lake:

```sql
SELECT count(*) AS files, sum(size) AS bytes FROM read_blob('.tmp/lake/data/**');
```

## Price and the free tier

From [pricing](https://www.backblaze.com/cloud-storage/pricing), 2026-10-06:

- Storage: the first 10 GB free; then $6.95/TB/month ($0.00695/GB). The upstream audit script's
  $0.006/GB is stale.
- Egress: free up to 3× the average stored data a month; $0.01/GB beyond.
- Transactions: Class A, B and C free; Class D free for the first 2,500 a day, then $0.004 per
  10,000.

Spec 001 aims the whole bucket under 100 MB with 30 days of snapshots (SC-005), 1% of the free
tier; the 30-day versions add at most the catalog's daily rewrites and what cleanup deletes.

Caps & Alerts (web UI, Account → Caps & Alerts) is a person's step. Whether B2 accepts a $0 cap
is **unverified**; spec 001 relies on the account having no card.

backblaze-labs/b2-mcp can be installed read-only to list and audit without the CLI:

and this skill's rules apply to it unchanged.
